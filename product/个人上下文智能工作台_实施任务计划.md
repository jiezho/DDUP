项目不从零开始。需求分析、UI/功能 Spec、高保真原型、竞品调研和 Runtime 评估已经完成；G1–G6b 已通过确认，G6a 已按 Windows Runtime Stop 收口，G6b-P1 已按供应链与默认能力面证据在安装前 Stop。核心项目闭环、权限优先全文检索、显式上下文篮、AnswerAttempt 安全检查、无持久化提取式逐句预检、Native 确定性 Run 生命周期、三类 Candidate/Approval、备份恢复、正式运行中心和全站响应式/PWA 门已经落地。Hermes 仍未安装、未连接，不计入 P1 可用能力。

后续按九个阶段推进：

1. 工程治理与现状基线；
2. MVP 范围冻结；
3. 架构、数据和权限冻结；
4. 基础平台与项目垂直闭环；
5. 个人上下文知识库与引用问答；

> 建立项目 → 汇聚文档和知识 → 讨论并形成决策 → 跨来源检索和带引用问答 → 形成任务 → 今日执行 → 日终复盘。

## 2. 执行与确认规则

### 2.1 任务状态

| 状态 | 含义 |
|---|---|
| `待开始` | 前置条件未满足或尚未排期 |
| `进行中` | Codex 正在生成、实现或验证 |
| `待确认` | 文档或演示已完成，需要用户作出产品/架构/授权决定 |
| `已确认` | 用户已明确接受或给出修改意见并完成修订 |
| `已完成` | 交付物、测试和文档均达到验收条件 |
| `已阻塞` | 存在无法在当前权限或上下文内解决的外部阻塞 |

### 2.2 Codex 可直接执行

- 读取、整理和交叉检查现有代码与文档；
- 在既定范围内创建或更新代码、测试和文档；
- 使用虚构演示数据完成开发和测试；
- 运行非破坏性的构建、测试、隐私扫描和页面验证；
- 修复不改变产品含义的缺陷、文档不一致和低风险工程问题；
- 输出差异、风险、截图、测试结果和后续建议。

### 2.3 必须由用户确认

- MVP 范围、优先级和明确非目标；
- 会改变使用模式的信息架构或关键交互；
- 技术栈、存储、部署、身份和公司数据边界；
- 新增生产依赖、外部云服务或可能持续产生费用的服务；
- 接入真实个人/公司资料、账号、密钥或第三方平台；
- 外部写入、发送消息、发布、删除、权限变更和不可逆迁移；
- Harness/Hermes 的正式纳入、发布范围和上线决定。

### 2.4 文档确认方式

需要确认的文档统一采用文件名后缀 `_待确认`，文首列出“需要确认的决定”和 Codex 推荐默认项。用户可以：

1. 全部同意；
2. 按编号修改某几项；
3. 要求补充备选方案或验证；
4. 暂缓某项并采用文档中的保守默认值继续不受影响的任务。

确认后移除文件名中的 `_待确认`，在文首记录确认日期和决定，并把关键技术选择写入 `product/ADR/`。

## 6. 任务交付完成定义

一个任务只有同时满足以下条件才标记为“已完成”：

1. 需求或问题有明确来源和范围；
2. 代码/文档变更与既有决策一致；
3. 对应测试、构建或人工验证已执行；
4. 演示数据明确为虚构，不含真实个人或公司信息；
5. 错误、空态、权限态和回退路径被考虑；
6. 变更影响、风险和未完成事项已记录；
7. 需要用户确认时已有明确确认记录；
8. 相关需求、Spec、API、测试和运行手册已同步。
9. 每次代码更新交付时已启动或验证本地回环试运行，并给出实际访问地址。
