# ADR-016：候选生成、审批决策与业务应用分离

> 状态：已接受
> 日期：2026-08-28
> 关联：ADR-005、ADR-015；S5-02

## 背景

Native Runtime 已能持久化 Run，但尚未证明 Runtime 请求业务工具时不会越权或把草稿直接写入项目真源。首个工具闭环需要同时验证 L1 自动候选、L2 显式批准、参数防替换、失败审计和幂等应用，而不能依赖模型“自觉”遵守规则。

## 决定

1. 首个 Runtime 可调用工具固定为 `candidate.task.create.v1`。输入必须来自用户明确提交的结构化 `task_candidate`；Native Runtime 不生成或改写标题、描述和日期。
2. L1 工具只能创建 `Candidate(status=pending)`，不得创建 Task。目标 Project 必须位于 Run 绑定的有效 ContextPackage 显式范围内，并再次通过空间、项目状态和 ToolCall 预算校验。
3. `candidate.apply.v1` 为 L2、不可由 Runtime 直接调用。Workbench 本地拥有者先创建 Approval，再显式 approve/reject，最后通过独立 apply 命令执行。
4. Approval 的 `scope_digest` 绑定动作、Candidate ID、Project ID 与不可变 proposal digest。resolve 和 apply 均重新计算实际 proposal digest；内容被替换、审批过期、版本过旧或主体/空间不匹配时失败关闭。
5. 批准不等于应用。只有 apply 的同一事务内才创建 `source_kind=ai_candidate` 的 Task、更新 Candidate、写 Audit/Outbox 与 L2 ToolCall；响应丢失后用幂等键回放，不重复创建任务。
6. ToolCall 只保存参数摘要，不保存候选正文。成功、越权拒绝和失败均有稳定状态与脱敏审计；L3/L4 工具继续不注册。

## 结果

- Runtime 可以提出任务候选，但不能批准自己，也不能直接修改项目真源。
- 用户可明确区分“候选”“已批准”“已应用”；拒绝、过期和参数替换不会产生 Task。
- Harness/Hermes 后续只需提交相同 ToolCall 契约，不能绕过 Workbench Registry、Policy 与 Approval Bridge。

## 当前限制

- 当前只实现 Task Candidate；知识、决策、复盘等候选仍待后续扩展。
- 正式待确认中心 UI 尚未实现；当前证据为本地 API、SQLite 状态、审计与契约测试。
- 没有外部动作，L3/L4 继续 disabled/unregistered。
