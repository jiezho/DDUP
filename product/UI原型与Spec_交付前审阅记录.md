# UI 原型与 Spec：交付前审阅记录

> 审阅日期：2026-08-18  
> 审阅对象：`/prototype` 高保真原型、UI/功能 Spec、上位需求分析  
> 结论：通过原型评审门，可进入产品评审；尚不代表生产就绪。

## 1. 审阅摘要

本轮从需求一致性、原型完整性、交互闭环、权限边界、移动端范围、可实施性和构建可用性七个维度进行审阅。

已确认：

- 八个核心工作区均有独立可点击页面；
- 项目工作台作为通用骨架，科研、AI 应用和学习作为专业模板，未重复建模；
- 个人上下文知识库明确覆盖全部授权模块，同时保留源权限；
- 英语作为学习提升中的首个方向，而不是独立一级系统；
- 天蓝色设计令牌、渐变、响应式布局和移动底栏均已实现；
- 全局搜索、快速捕获、新建项目、AI 助手和讨论转决策可交互；
- Spec 提供页面、组件、数据、权限、AI、移动端、接口和验收规格；
- 最终生产构建通过。

## 3. 发现与处置

### R-01：搜索快捷键与界面提示不一致

- 严重度：主要；
- 发现：界面展示 `⌘/Ctrl + K`，原始原型未绑定键盘行为；
- 处置：已增加全局快捷键，并增加 Esc 关闭导航、弹窗和助手；
- 状态：已关闭。

### R-02：创建项目后的落点与 Spec 不一致

- 严重度：主要；
- 发现：初稿仅回到项目组合，Spec 要求进入新项目总览；
- 处置：已修改为创建成功后进入新项目总览并显示成功反馈；
- 状态：已关闭。

### R-03：移动底栏命名不一致

- 严重度：次要；
- 发现：Spec 与原型对“知识/我的/问 AI”的命名不一致；
- 处置：Spec 已统一为“今日、项目、捕获、问 AI、知识”；
- 状态：已关闭。

### R-04：原型小字号不适合作为最终生产规范

- 严重度：主要但不阻塞原型评审；
- 发现：部分元信息为 8–10 px，适合高密度概念稿，但正式产品可读性不足；
- 建议：视觉定稿时将正文最低字号提升至 12 px，元信息最低 10–11 px，并在 100%/125% 系统缩放下检查；
- 状态：进入设计系统 TODO。

### R-05：弹窗无完整焦点圈定

- 严重度：主要但不阻塞原型评审；
- 发现：已支持 Esc，但尚未实现焦点陷阱、关闭后焦点归位和完整键盘顺序；
- 建议：研发版采用成熟 Dialog primitive 或实现 WAI-ARIA 对话框模式；
- 状态：进入前端 TODO。

### R-06：数据与 AI 行为均为演示态

- 严重度：预期限制；
- 发现：原型使用合成数据和本地组件状态；
- 处置：Spec 第 0、12、14 节已明确原型与生产边界；
- 状态：接受，不构成缺陷。

### R-07：前端主包体积较大

- 严重度：次要；
- 发现：生产构建的主 JavaScript 约 1.54 MB，gzip 后约 464 KB；构建给出大 chunk 提示；
- 建议：研发阶段按路由拆分页面、延迟加载图表/编辑器/图标，并设置体积预算；
- 状态：进入性能 TODO。

### R-08：移动连接器尚未实装

- 严重度：预期限制；
- 发现：响应式 Web 已表现，但飞书/微信只是产品设计；
- 处置：Spec 已定义首期能力、安全策略和实施阶段；
- 状态：接受，后续实施。

## 5. 下一步路线

建议按以下顺序推进：

1. 召开原型评审，集中确认 Spec 第 16 节的八个产品决策；
2. 根据评审结论完成字号、组件状态、空态和权限态视觉定稿；
3. 将 MVP-1 拆为项目域、今日/捕获、搜索、身份与空间、基础知识库五个研发包；
4. 在真实数据接入前先确定统一对象 ID、空间策略、来源引用和审计模型；
5. 性能、无障碍和移动连接器在研发验收中作为明确门槛，不留到发布前补做。

## 7. V1.1 Agent Runtime 增量审阅

> 增量审阅日期：2026-08-19  
> 审阅对象：Harness/Hermes 融合决策、需求 V1.2、UI Spec V1.1、Prototype 0.2  
> 判断：通过方案一致性门；两个 Runtime 均未安装，不得表述为真实接入完成。

### 7.1 核心主张审计

| ID | 主张 | 审阅结论 | 处置 |
|---|---|---|---|
| RC1 | Harness 可作为主候选执行层 | 有官方跨进程 SDK 和插件边界支持；但 Developer Preview 风险高 | 限定为固定版本、独立进程、只读 POC |
| RC2 | Hermes 可带来实际补充 | 消息网关、HTTP/JSON-RPC 接入和多环境执行有明确依据 | 只保留移动网关、备选 Runtime、技能候选三项测试 |
| RC3 | Harness 与 Hermes 应深度互嵌 | 两者 Agent Loop、工具、记忆、调度和子 Agent 高度重叠 | 否决；一个 Run 一个主 Runtime |
| RC4 | Hermes 记忆可直接成为个人知识库 | 会造成双真源、来源不清与权限污染 | 否决；只生成待确认知识/记忆候选 |
| RC5 | 原型表示真实运行状态 | 当前没有安装或连接任一 Runtime | 明确标记“隔离 POC”“候选，未连接” |

### 7.2 主要风险与修订结果

- **过度承诺风险：已修订。** 所有页面和文档均区分“方案/POC/候选/已实现”；Hermes 没有启用按钮。
- **双重编排风险：已修订。** 在需求、Spec、架构和原型中统一为“一个 Run 一个主 Runtime”。
- **知识双真源风险：已修订。** Workbench 个人上下文知识库为唯一真源；Runtime 内部记忆仅能产生候选。
- **消息入口越权风险：仍需实验。** Hermes 的平台 allowlist 不能替代 Workbench 空间与对象权限，POC 必须做二次授权和泄露测试。
- **Windows 隔离风险：仍需实验。** 两个项目都不能仅凭文档视为已满足生产隔离；目标部署优先 Docker/远程沙箱。
- **维护成本风险：保留停止条件。** Hermes 若不能显著降低消息接入成本或在专项任务胜出，应停止该分支。
